# ADR-002 — A deterministic state machine inside one job, review rounds as self-dispatched runs

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D2 Control flow

## Context

The stages have back-edges:
- test failure → implementation
- repeated test failure → design
- review findings → design, implementation or tests

GitHub Actions jobs form a DAG with no loops. We also want every back-edge decision to be explainable
after the fact from the artifacts. An LLM "planner" that chooses the next step adds a non-reproducible
decision on top of non-reproducible agents.

## Decision

1. **Stages 1–4 run in one Actions job (`agents`), driven by a Python Controller that is a fixed
   state machine.** The states are `SPEC → SPEC_CHECK → DESIGN → DESIGN_CHECK → BUILD → BUILD_CHECK →
   TEST → TEST_CHECK → DONE | STOPPED(reason)`. The back-edge rules are code:
   - spec/design check fails → same agent once more with the check output, then stop;
   - build check fails → Builder again (counts against 3 Builder attempts);
   - tests fail → Builder again with the failing pytest output; after the 2nd failed attempt →
     Architect once (redesign with test_report), then Builder;
   - tests missing for an AC → Tester once more.
2. **Stages 5 and 6 are separate jobs** (`release` → `ci` → `review` → `post-review`). They are
   separate because they need different permissions (ADR-005, ADR-008), not because of control flow.
3. **Review rounds are new workflow runs.** After a `request_changes` verdict, `post-review` calls
   `workflow_dispatch` on the same workflow with `mode=rework, round=r+1, target=<stage>,
   pr=<n>`. The Controller then re-enters at the stage the reviewer named (design, implementation or
   tests) with the review findings as extra input. This continues until approval or round 2 is used up.
   `workflow_dispatch` is the one event that `GITHUB_TOKEN` is allowed to trigger.
4. **Who decides to go back:** inside a run, only the Controller's rules. In review, the Reviewer
   *proposes* the target stage in its verdict, and the poster enforces the round budget.

## Alternatives considered

- **LLM orchestrator with workers** (a planner chooses the next stage). It is more flexible, for
  example it could skip design for a one-line fix. We rejected it because its routing is
  non-deterministic, harder to bound, and another place where injected text could steer control.
- **Unrolled jobs** (`review_1 → rework_1 → review_2 → …` in one YAML). The whole story is visible in
  one run graph. But the YAML repeats itself and the round limit is hard-coded into the job graph.
- **One job per stage chained by artifacts.** It gives clean permissions per stage. But loops between
  stages 3 and 4 would need dispatches too, and each job pays roughly 30–60 s of setup. Stages 1–4
  share the same permissions anyway (read-only token plus model key).

## Consequences

- Back-edges are reproducible and easy to read in `state.json` (`history` lists every transition and why).
- A review round shows up as a *separate* Actions run. `runs.md` and the issue's state comment link them.
- A fixed pipeline always runs design, even for trivial issues. That costs extra tokens.
- `workflow_dispatch` needs `actions: write` in `post-review`. That job never holds the model key.
