# ADR-005 — Hand-written function tools per agent, GitHub access only in deterministic jobs

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D5 Tools

## Context

The tool sets differ by agent:
- the Analyst needs to read;
- the Builder needs to edit and run tests;
- the Reviewer needs to read and run but must not push or post.

A generic shell tool or the GitHub MCP server would give every agent far more than it needs. The MCP
server's tools include creating branches, pushing files and merging, and scoping them per agent means
trusting a configuration layer we do not control.

## Decision

1. **Agents get hand-written Gemini function-calling tools** (`autose/tools.py`), registered per agent:

   | Tool | Analyst | Architect | Builder | Tester | Reviewer |
   |---|---|---|---|---|---|
   | `list_files`, `read_file`, `search_code` | ✓ | ✓ | ✓ | ✓ (base commit) | ✓ (PR head) |
   | `write_file`, `replace_in_file` | | | ✓ `tinydb/**`, `docs/**` | ✓ only `tests/test_autose_issue_<n>.py` | |
   | `check_build` (compileall + import) | | | ✓ | | |
   | `run_tests` (fixed `python -m pytest` argv; the agent picks only test paths/`-k`) | | | ✓ | ✓ | ✓ |
   | `run_python` (a snippet in the sandbox, 60 s) | | | | | ✓ |
   | `submit` / `submit_review` (ends the session, returns the artifact) | ✓ | ✓ | ✓ | ✓ | ✓ |

   Every path is resolved and checked against a jail. `..`, symlinks out of the tree, `.git/`,
   `.github/` and `autose/` are refused. Tools that run code run as a separate unprivileged OS user
   (`autose-sandbox`), with an empty environment (no `GEMINI_API_KEY`, no `GITHUB_TOKEN`), a timeout,
   and output truncated to 8 KB.
2. **No agent has git, network or GitHub tools.** The Controller does `git` locally. Release pushes
   and opens the PR with the **REST API via `requests`** and the job's `GITHUB_TOKEN`. That job runs
   no model and executes no model-written code apart from copying the bundle.
3. **Permissions by job** (top-level `permissions: {}`):

   | Job | GITHUB_TOKEN scopes | Model key |
   |---|---|---|
   | gate | issues: write (acknowledgement comment only), pull-requests: read | no |
   | agents | contents: read, actions: read | yes |
   | release | contents: write, pull-requests: write, issues: write | no |
   | ci | contents: read | no |
   | ci-status (posts the CI result as a commit status on the PR head) | statuses: write, issues: write, pull-requests: write | no |
   | review | contents: read, issues: read, pull-requests: read | yes |
   | post-review | pull-requests: write, issues: write, actions: write | no |

   Checkouts use `persist-credentials: false`, so the token is not left in `.git/config` for agent
   code to find. Jobs that hold the model key never `pip install -e .` the checkout: tinydb is imported
   through `PYTHONPATH`, so no build backend from a PR can run before the key is present. The
   Controller's own build check (compileall + import) also runs in the sandbox.

## Alternatives considered

- **GitHub MCP server / `gh` CLI exposed to agents.** Agents could open the PR themselves. But the
  capability is too broad and we would depend on the toolset filtering being right.
- **A generic `bash` tool with an allowlist.** More flexible for the agent. But shell allowlists are
  easy to bypass (`python -c`, pipes, `$(...)`).
- **An off-the-shelf "fix this issue" action** (e.g. a coding-agent action). Fast to set up, but it
  hides the tool loop and the permission model we are asked to justify.

## Consequences

- Building our own tool loop (around 300 lines) costs effort and may be less capable than a mature agent harness.
- The Builder cannot install packages or use the network. tinydb has no runtime dependencies, so this is fine.
- The sandbox user is created with `sudo useradd` on the GitHub runner. In a local dry run (no sudo)
  the tools fall back to scrubbing the environment only, and the run log says so.
