# ADR-007 — Checks are deterministic wherever possible, the LLM judges only testability, and code decides

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D7 Checks

## Context

Every stage has a check. An agent that says "done" is not evidence that it is done. LLM judges are
cheap to write but unreliable and open to persuasion. Deterministic checks are reliable but can only
check structure. We want each check to be as strong as the stage allows, with a single, auditable
decider.

## Decision

The **Controller** (code) makes every pass/fail decision. Its rule for each check:

| Stage | Check | Kind |
|---|---|---|
| 1 Spec | `spec_lint`: ≥1 AC, every AC has an id `AC-n`, Given/When/Then lines, and at least one code-level observable (backticked call, value or exception); no A1 vague words (fast, robust, user-friendly, etc.) inside ACs. **AND** `spec_judge`: an LLM call that returns JSON `{AC-n: {testable: bool, reason}}`. All must be true. | deterministic + LLM |
| 2 Design | `design_check`: `## Files to change` table parsed. Each path exists or is marked NEW under an allowed root. Each named function/class is found by `ast` in that file or marked NEW. Each AC id appears in the `AC mapping` section. | deterministic |
| 3 Build | Non-empty diff; every changed path is in the allowlist; `python -m compileall -q tinydb`; `python -c "import tinydb"`. | deterministic |
| 4 Test | AC coverage by name (`test_ac<k>_…` for every k); `pytest tests/test_autose_issue_<n>.py` passes; the **full suite** passes; red-on-base recorded (new tests run against base `tinydb/`) for information. | deterministic |
| 5 Release | The REST API reports the PR `state == open`; the reusable CI job on the head sha concludes `success` (posted on the PR head as the commit status `AutoSE CI (stage 5)`). | deterministic |
| 6 Review | `verdict.json` matches the schema. An `approve` is accepted only if the Reviewer's *tool log* (recorded by our harness, not self-reported) contains at least one `run_tests` call on the PR head, and the verdict lists ≥1 checked requirement. Otherwise it is recorded as `request_changes (insufficient evidence)`. A reviewer that never submits is recorded as `inconclusive`: posted, no rework dispatched, left to a human. | deterministic over LLM output |

## Alternatives considered

- **LLM judge for every stage** ("is this design good?"). Easy to write, but the judge can be argued
  with by the very text it judges, and it gives a different answer on a re-run.
- **Purely deterministic spec check.** Cheap, but structure does not imply testability. "Then results
  are correct" passes a Given/When/Then lint.
- **Mutation testing as the Stage 4 check.** A stronger test-quality signal, but too slow and too
  noisy inside a run budget. We record red-on-base as a cheaper stand-in.

## Consequences

- The checks can be gamed structurally. For example, the Tester could name a trivial test `test_ac1_x`.
  Red-on-base reporting and the independent Reviewer are the backstops.
- Red-on-base is *not* required to pass. Some correct ACs (for example "existing behaviour unchanged")
  are green on base by design.
- The spec judge is the only LLM-decided check. Its JSON is stored in `spec.md`'s appendix for audit.
