# ADR-008 — Reviewer independence through job, token, model, inputs and a checklist that needs evidence

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D8 Reviewer independence

## Context

A reviewer that shares the implementer's context or model tends to approve. Our A2 experience showed
an agent rating its own diff as "consistent with the architecture" when hidden tests disagreed. The
assignment allows the Reviewer to see only the issue, the diff and the repository at the PR head. It
may run code but must not push.

## Decision

Independence is enforced in five layers, each of which works without the others:

1. **Separate job on a fresh runner (`review`).** It never downloads the `agents` artifacts. It checks
   out the PR head sha and deletes `.autose-run/` if present.
2. **Separate token.** `contents: read`, `issues: read`, `pull-requests: read`. It *cannot* push,
   comment or approve. Posting is done by the separate `post-review` job, which has no model key.
3. **Separate model.** `AUTOSE_REVIEWER_MODEL` (default Pro) ≠ `AUTOSE_WORKER_MODEL` (Flash).
4. **Separate inputs.** Issue + `git diff base...head` + repo. No spec, design, test report, PR body
   or transcript. Commit messages are neutral (`autose: changes for #n`), so no reasoning leaks
   through git history.
5. **An adversarial prompt with required evidence:**
   - The Reviewer must first derive its own list of requirements *from the issue* (R1..Rn) before it
     reads the diff.
   - For each Rn it must say how it verified it: a test it ran, a snippet it executed, or code it read.
   - It must try at least one edge case not covered by the PR's tests, using `run_python` or a scratch
     test (it can write only to a temp dir).
   - The default verdict is `request_changes`. Approval must be argued.
   - Each finding is given a `target` stage (design, implementation or tests) for routing.

   ADR-007 then rejects an approval that has no `run_tests` call in the harness's tool log.

## How we check it does not rubber-stamp

- **Seeded PRs (experiment/seeded_prs):** five human-made PRs. Some have planted defects (a wrong
  edge case, an existing behaviour broken by an untested path, an injection attempt in a docstring)
  and some are good changes. We measure catch rate and false-alarm rate.
- **Decision experiment 1** compares this Reviewer with a "coupled" variant: worker model, a friendly
  prompt, and it sees the PR body written by the author.

## Alternatives considered

- **Same job, new chat session.** Cheap, but the token, the filesystem (spec/design files) and the
  model are shared. Independence would hold only by convention.
- **Reviewer allowed to see spec.md.** It would catch spec-vs-code drift, but it would also inherit
  any misreading of the issue by the Analyst, which is the error we most want caught.
- **GitHub `APPROVE` review event.** We deliberately post `COMMENT` with the verdict in the body, so
  a bot approval can never satisfy branch protection. The human decides.

## Consequences

- A stricter reviewer raises false alarms. Each one costs a rework round (bounded at 2).
- Without the spec, the Reviewer may object to an assumption the Analyst documented. That is useful:
  it shows the assumption to the human.
