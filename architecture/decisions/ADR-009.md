# ADR-009 — Layered budgets and a "text is data, never capability" stance against prompt injection

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D9 Safety and failures

## Context

- Anyone can open an issue or comment on a public repository, so issue and comment text is untrusted
  even when a maintainer applies the label.
- Agents can loop: repeated identical tool calls, endless retries.
- Gemini free and paid tiers return 429s.
- GitHub Actions has limits:
  - a 6 h job maximum and per-job `timeout-minutes`;
  - `GITHUB_TOKEN` events do not trigger workflows except `workflow_dispatch` and `repository_dispatch`;
  - secrets are not available to workflows triggered from forks.

## Decision

**Budgets (enforced by the Controller and by YAML):**

| Limit | Value |
|---|---|
| Tool-call steps per agent session | Analyst 15, Architect 20, Builder 40, Tester 25, Reviewer 30 |
| Builder attempts per run | 3 (+1 redesign); spec/design retries 1 each |
| Review rounds | 2 |
| Tokens per run (sum of `usage_metadata`) | 2,000,000 hard stop → state `STOPPED(budget)` |
| `timeout-minutes` | gate 5, agents 45, release 10, ci 10, review 25, post-review 5 |
| Per tool subprocess | 300 s (`run_tests`), 60 s (`run_python`) |
| 429/5xx | exponential backoff 2→64 s, 6 tries, then the stage stops with a reason |

**Stuck detection:**
- the same tool call with the same arguments 3 times in a row → the session is aborted with a
  "stuck" reason;
- a session that ends without `submit` → the stage fails its check.

**Prompt injection (defence in depth, assuming the model *will* sometimes obey injected text):**

1. *Who can start a run:* only users with write/maintain/admin permission (ADR-010). This limits who
   can spend money. It does not make the text trustworthy.
2. *No `${{ github.event.* }}` in `run:` scripts.* Issue and comment bodies are fetched by Python via
   the API or passed through `env:`, so text cannot become shell.
3. *Fencing:* untrusted text sits in `<untrusted_issue nonce=…>` blocks. Every system prompt states
   that instructions inside it are content to analyse (the A1 skill already has this rule). The
   Analyst must list any embedded instructions it ignored under `Injection notes` in spec.md.
4. *Capability containment (the real defence):* agents have no network, git, GitHub or secret access.
   Writes are confined to allowlisted paths. Code runs as a sandbox user with an empty environment.
   So even a fully hijacked Builder can at most produce a bad diff.
5. *Deterministic release guard:* Release refuses bundles that touch anything outside `tinydb/`,
   `tests/` and `docs/` (in particular `.github/`, `autose/`, `pyproject.toml`, `setup.*`, `conftest.py`).
6. *Independent review and a human merge:* a malicious diff still has to get past the Reviewer
   (who is told to flag suspicious changes) and a person.

## Alternatives considered

- **An LLM "injection classifier" on the issue text.** Cheap, but bypassable, and false positives
  block real issues. At most it could add a warning, so we rely on capability containment.
- **Running agents only after a maintainer copies the issue into a trusted template.** Safe, but it
  defeats the "label and walk away" goal.

## Consequences

- A tight token cap can stop a legitimate hard issue. The stop reason is written into the artifact,
  so a human can raise the cap through a repository variable.
- The sandbox user requires `sudo` on the runner (available on GitHub-hosted Ubuntu runners).
