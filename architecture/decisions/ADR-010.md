# ADR-010 — A label or a `/autose` comment from a write-access user; one queued run per issue

- **Status:** Accepted (design-time, 2026-11-20)
- **Decision area:** D10 Triggers

## Context

- Maintainers want to "add a label and walk away", but also to re-trigger and to ask for a review on
  an existing PR.
- Starting a run costs money and creates branches, so only trusted users may start one.
- Two runs for the same issue at once would race on the branch and the PR.
- Runs started by our own bot must not cause loops.

## Decision

**Events:**

| Event | Condition | Mode |
|---|---|---|
| `issues: labeled` | label name is exactly `autose` | `full` (round 1) |
| `issue_comment: created` on an issue | body's first line is `/autose` | `full` (round 1, restarts the issue) |
| `issue_comment: created` on a PR | body's first line is `/autose review` | `review-only` (stage 6 on that PR, used for seeded PRs) |
| `workflow_dispatch` | inputs `issue`, `mode` (`full`, `rework`, `review-only`), `round`, `target`, `pr`, `variant` | used by `post-review` for rounds, and by maintainers for experiments |

**Who may start a run:**
- *Job-level `if`:* the sender is not a bot, and `author_association` ∈ {OWNER, MEMBER, COLLABORATOR}
  (for comments).
- *Gate job:* it calls `GET /repos/{repo}/collaborators/{sender}/permission` and requires `admin`,
  `maintain` or `write`.
- Adding a label already requires triage or higher, but triage alone is rejected by the gate.
- `workflow_dispatch` requires write access by GitHub's own rules.

**Concurrency:** job-level groups, `cancel-in-progress: false`:
`autose-agents-<issue>`, `autose-release-<issue>`, `autose-review-<pr or issue>`, `autose-post-review-<pr or issue>`.
They are job-level, not workflow-level, because every issue comment starts the workflow. A skipped
comment run in a workflow-level group could replace a pending real run.
- A second trigger for the same issue *waits* until the first finishes. GitHub keeps at most one
  pending run per group and replaces an older pending one.
- Different issues run in parallel on their own branches (`autose/issue-<n>`).
- Review-only runs are grouped by PR, so ten `/autose review` comments on five PRs do not cancel each other.

**Loop prevention:**
- Comments posted by the workflow start with `🤖 AutoSE`, and they come from `github-actions[bot]`.
  Bot senders are ignored.
- Events created with `GITHUB_TOKEN` do not trigger runs anyway. The only bot-made trigger is the
  explicit `workflow_dispatch`, whose round counter ADR-004 bounds.

## Alternatives considered

- **Trigger on `issues: opened`.** Fully automatic, but it lets any stranger spend our budget.
- **`cancel-in-progress: true`.** The newest request wins. But it can kill a run half-way through
  pushing, leaving a branch and PR that do not match. Queueing is safer and the delay is acceptable.
- **`pull_request_target` for review-only.** It runs with secrets on fork PRs, which is a known
  injection hazard. We use an explicit comment command from a trusted user instead.

## Consequences

- A maintainer who labels and then also comments `/autose` gets two sequential runs. The second one
  restarts round 1 and is visible in the state comment.
- Secrets are not exposed to fork PRs, because nothing runs on `pull_request` with secrets.
