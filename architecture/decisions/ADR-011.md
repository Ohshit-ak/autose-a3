# ADR-011 — Gemini 3.5 Flash for workers (low thinking), Gemini 3.6 Flash for the Reviewer

- **Status:** Accepted (2026-11-20). **Supersedes [ADR-006](ADR-006.md).**
- **Decision area:** D6 Models

## Context (what we learned)

ADR-006 chose `gemini-2.5-flash` for the workers and `gemini-2.5-pro` for the Reviewer. Before the
first Actions run, the Controller's start-up model check (ADR-006 itself required it) and a probe
with the project key showed the following (2026-11-20):

| Model | Listed by `models.list` | `generateContent` |
|---|---|---|
| gemini-2.5-flash / gemini-2.5-pro | yes | **404 "no longer available to new users"** |
| gemini-4-argon / carbon / neon | yes | 429 quota exhausted on this tier |
| gemini-4-hydrogen | yes | worked, but about 96 s for one trivial function call |
| gemini-3.7-flash / 3.8-flash | yes | 503 high demand at probe time |
| gemini-3.5-flash / gemini-3.6-flash | yes | worked; about 50–60 s per trivial call with default thinking, **about 15 s with `thinking_level=low`** |

So the listing is not proof of availability. Latency, not price, is the binding constraint: an
agents job makes on the order of 50–150 model calls.

## Decision

- **Workers** (Analyst, Architect, Builder, Tester, spec judge): `gemini-3.5-flash` with
  `thinking_level=low` (`AUTOSE_WORKER_MODEL`, `AUTOSE_WORKER_THINKING`).
- **Reviewer**: `gemini-3.6-flash` with the model's default (deeper) thinking (`AUTOSE_REVIEWER_MODEL`).
  It is a *different* model from the workers, so ADR-008's model-diversity layer still holds, and it
  gets more thinking per call than the workers.
- Job timeouts raised: `agents` 45 → 120 min, `review` 25 → 60 min.
- The start-up check stays, and is extended in spirit: a model must answer a real call, not only be listed.

## Alternatives considered

- **gemini-4-hydrogen as the Reviewer** (likely the strongest available). We rejected it because
  ~96 s per trivial call × ~30 reviewer steps would exceed the review budget, and its siblings were
  quota-exhausted.
- **Default thinking for the workers.** It may be better quality, but 3–4× slower per call, so a run
  would not fit the job timeout.

## Consequences

- The Reviewer is no longer clearly *stronger* than the workers, only different and given more
  thinking. Decision experiment 1 measures whether that is enough.
- Results depend on Gemini 3.x versions that were available on the run date (a threat to validity).

## Amendment (2026-11-21): lite models and per-role model pools

**What the first real runs showed.** Run [44788437645](https://github.com/Ohshit-ak/tinydb/actions/runs/44788437645)
(issue #3) stopped cleanly on its first call with `QuotaExhausted` (ADR-009 guard). The key is on the
Gemini free tier: **20 requests per model per day**, for the lite models as well. A local dry run
the next day used 15 requests on `gemini-3.5-flash-lite` (it got through stage 1, where the spec
lint correctly rejected an AC containing "correctly" and sent it back) before that model's quota ran out.
No paid tier was available.

**Change.**
- The default models are now `gemini-3.5-flash-lite` for the workers (about 2 s per call) and
  `gemini-3.1-flash-lite` for the Reviewer.
- Each role has a **pool** of models. When the current model's daily quota is spent, or it stays
  unavailable (503), `llm._generate` moves to the next model *of the same pool*:
  - worker pool: 3.5-flash-lite → 3.5-flash → 3.6-flash → 3.8-flash;
  - reviewer pool: 3.1-flash-lite → 3.7-flash → 4-hydrogen.
- The pools are disjoint, so the Reviewer never uses a worker model (ADR-008).
- The actual model of every call is logged in `usage.jsonl`.
- When switching models in the middle of a session, earlier thought signatures are replaced by
  Gemini's documented bypass value.
- Step budgets were lowered: Analyst 10, Architect 12, Builder 20, Tester 12, Reviewer 15.

**Consequences.**
- The total capacity is about 80 worker and 60 reviewer requests per day, so only a few runs fit per
  day. The experiment plan is scaled down accordingly (see `experiment/variants.md` and the report).
- A run can mix models from one pool. The models actually used are reported per run.
- **Separate keys and projects (2026-11-21).**
  - The Reviewer runs on its own Gemini key from a different Google project (secret
    `GEMINI_REVIEWER_API_KEY`), so it shares neither model nor quota with the implementer.
  - The worker agents get an ordered list of keys (`GEMINI_API_KEYS`, built from `GEMINI_API_KEY` and
    `GEMINI_API_KEY_2`) and move to the next key only when every model of their pool is exhausted
    on the current one.
  - Keys exist only as repository secrets, injected into the `agents` and `review` jobs.
  - *Note:* using several free projects to stay within free-tier limits is a trade-off against the
    provider's usage terms. A paid tier would be the production choice.
- **Reviewer quota fallback (2026-11-21, evidence: [run 44910096582](https://github.com/Ohshit-ak/tinydb/actions/runs/44910096582)).**
  - Five seeded-PR reviews ran in parallel and exhausted the reviewer key's free quota on all four
    reviewer models. Two earlier reviews had also hung for 40+ minutes on a single request, because
    the client had no request timeout, and were cancelled by the 60-minute job timeout.
  - Now every request has a 90 s timeout, and a timeout is retried or falls back like a 503.
  - The review job tries the reviewer key first and then the worker keys, but **only with
    reviewer-pool models**. When that happens, the Reviewer shares a Google project (not a model, job,
    token or context) with the implementer, which weakens one of ADR-008's five layers.
  - A review that still finds no quota is posted as `inconclusive` (no rework, a human decides)
    instead of failing the job.
