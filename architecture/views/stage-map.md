# Stage map — agent, artifact and check per stage

| # | Stage | Agent | Artifact | Check (who decides) | On failure |
|---|---|---|---|---|---|
| 1 | Requirements | **Analyst** (A1 `requirements-spec` skill, unattended mode) | `spec.md` | Deterministic lint: every AC has an ID `AC-n`, Given/When/Then, and a concrete observable (a call, a value or an exception), with no vague words. **Plus** an LLM spec judge that marks each AC testable or not, with a reason. The Controller passes only if both pass. | 1 retry with the check feedback. Then stop, with the reason written into `spec.md`. |
| 2 | Design | **Architect** (uses `ARCHITECTURE.md` from A2) | `design.md` | Deterministic: a `Files to change` table. Every path exists, or is marked NEW under `tinydb/`, `tests/` or `docs/`. Every function named is found in that file by AST, or is marked NEW. Every AC is mapped to at least one change. | 1 retry. Then stop, with the reason in `design.md`. |
| 3 | Implementation | **Builder** | `diff.patch` (base...work) | Deterministic: the diff is not empty, it only touches allowlisted paths, `python -m compileall tinydb` passes, and `import tinydb` works. | Builder retry, within the attempt budget (3). |
| 4 | Testing | **Tester** writes `tests/test_autose_issue_<n>.py` from the ACs. The Controller runs the suites. | `test_report.md` | Deterministic: at least one `test_ac<k>_*` per AC, the new tests pass on the work tree, and the **full** existing suite passes. Whether the new tests fail on the base commit is recorded for information. | Failing tests go **back to stage 3** with the pytest output, up to 3 Builder attempts. After the 2nd failed attempt the Controller goes **back to stage 2** once (redesign). If the budget runs out it stops, with the reason in `test_report.md`. Missing AC coverage gets 1 Tester retry. |
| 5 | Release | **Release** (deterministic, no LLM) | `pr.md` + PR link | Deterministic: the PR exists and is open (REST), and the reusable `ci.yml` job on the head sha succeeds. | Stop, label `autose:failed`, and write the reason in `pr.md` and in an issue comment. |
| 6 | Review | **Reviewer** (separate job, different model, read-only token) | `review.md` (+ `verdict.json`) | Schema-valid verdict. An approval is accepted only if the reviewer's tool log shows it really ran the tests and checked each requirement it took from the issue. Otherwise it is downgraded to request_changes. | `request_changes` → `workflow_dispatch` rework round going to the stage the reviewer names (design, implementation or tests), **at most 2 rounds**. After that, label `autose:ready-for-human`. |

A person always makes the final merge or close decision. The workflow never merges, and it posts
reviews as `COMMENT`, never as `APPROVE`, so a bot approval can never count toward branch protection.
